# Customer Churn Analysis

Analysis of subscription-customer data to find the patterns behind cancellations, measure which behaviours drive churn, and suggest retention improvements.

> Task ID: `task2` (virtualwork.in) – Customer Churn Analysis

## Objective
- Analyse user activity, engagement and behavioural trends
- Identify the key factors that lead to churn
- Recommend improvements for retention

## Dataset (`data/customers.csv`, 5,000 customers)
Synthetic dataset generated by `generate_data.py` (seed 42) mirroring the task brief.

| Column | Meaning |
|---|---|
| tenure_months | How long the customer stayed |
| plan / monthly_fee | Basic / Standard / Premium |
| logins_per_month | Login frequency |
| days_since_last_login | Inactivity (14+ days = at risk) |
| support_contacts | Number of support contacts |
| feature_errors | Times a specific feature broke |
| churned | 1 = cancelled, 0 = active |

## How to run
```bash
pip install -r requirements.txt
python generate_data.py
python churn_analysis.py
```

## Key findings
- **Inactivity is the strongest signal:** 14+ days without login → **57.5%** churn vs **18.1%** otherwise.
- **Feature errors hurt:** 3+ errors → **46.8%** churn vs **17.4%** with none.
- **Early-life churn:** 0–6 month customers churn at **42.1%** vs **19.1%** for 25+ months.
- More support contacts and lower login frequency also raise churn.
- Random Forest: accuracy **75.8%**, ROC-AUC **0.776**. Top predictors: `days_since_last_login`, `tenure_months`, `logins_per_month`.

## Retention recommendations
1. Send a win-back nudge at 7 days of inactivity, before the 14-day cliff.
2. Fix repeatedly failing features first; alert support after 2 failures.
3. Build a 90-day onboarding programme for new users.
4. Proactively contact users with 3+ support tickets and solve the root cause.
5. Offer targeted discounts/upgrades to high-risk Basic-plan users.
